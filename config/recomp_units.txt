; Seed states for the routine-level lockstep gate, `dream_harness --unit`
; (tools/recomp_verify.py --units runs it; recomp/README.md documents the mode).
;
; Some routines in this port are reachable by nothing at all: command handlers no
; live 65816 code sends, sequence opcodes no song or sound-effect bank uses, stale
; jump-table slots, the one-row OAM emitters no sprite frame is short enough for,
; the animation-rate entries no table word points at, the `rti` at the unused
; vectors, and the five 65816 routines with no caller anywhere in the ROM. No
; input script can enter them, so the frame gate cannot credit them, and
; config/recomp.txt used to list them as unverified.
;
; A seed line puts a routine in a plausible machine state and has the ROM's own
; code and the C body run it from there. Every seven compared regions, every
; register and the cycle counts must agree afterwards, exactly as in the frame
; gate but at the granularity of one routine.
;
;   name  script  frame  key=value ...  ; note
;
; `name` is the routine, on either processor (the two registries are searched in
; turn). `script` is an input script under recomp/harness/inputs and `frame` how
; many frames to run it for: the harness boots the ROM that far, so WRAM, VRAM,
; CGRAM, OAM, ARAM, the DSP and the SPC registers hold content the game itself
; produced. It then parks the machine just past the end of vblank with NMI and
; both timer IRQs off, loads that state into two machines, applies the keys
; below to both, and runs.
;
;   end=ADDR    one past the last byte the routine occupies, in the same form as
;               the entry address ($C0:0000+offset for the 65816, the SPC's own
;               16-bit address). Control has left the routine when the pc goes
;               outside [entry, end) from an instruction inside it with no frame
;               of its own still on the stack. Where a body runs on into a
;               shared tail (the animation-rate chain into anim_rate_store,
;               orphan_slide_down2 into seq_advance5), `end` covers the tail
;               too, because that is what the ROM executes next as well.
;   ret=rts|rtl|rti|jmp|ret
;               which return frame to push before the routine starts. The
;               address pushed is a sentinel no routine owns, so returning
;               always leaves the range and no instruction at it is ever
;               fetched. `jmp` pushes nothing, for a routine that leaves through
;               a tail jump. `ret` is the SPC700's return.
;   stack=HH..  extra bytes pushed on top of the return frame, first byte
;               pushed first. Two callers in this ROM leave something there:
;               the animation-rate handlers' caller leaves one $80 byte for the
;               tail's `plb`, and seq_fetch pushes the slot index before it
;               dispatches a sequence-opcode handler.
;   a= x= y= p= db= dp= sp=      65816 registers (p is the flag byte)
;   a= x= y= psw= sp=            SPC700 registers
;   ram:ADDR=VV or VVVV          a byte or a little-endian word into the 65816
;                                bus address space
;   aram:ADDR=VV or VVVV         the same into the SPC700's ARAM
;   port:N=VV                    an APU input port ($F4-$F7 as the SPC sees it)
;   dsp:RR=VV                    a DSP register
;   dspadr=VV                    what $F2 points at
;
; Everything a line does not name keeps the value the booted machine had, which
; is the point: the seeds vary what the routine reads and leave the rest of the
; console alone. Four seeds per routine at least, including the edge values the
; routine's own bounds allow.
