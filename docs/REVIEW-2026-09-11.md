# Independent review, 2026-09-11 (commit efcce4c)

Scope: the whole repository. Read-only review. Nothing here was fixed.

What the review was measured against, from `CLAUDE.md`, `docs/LEGAL.md`, `docs/RECOMP.md`,
`README.md` and `recomp/README.md`:

1. `make check` rebuilds the ROM byte-identically from `src/` plus data extracted from the
   user's own ROM.
2. `tools/recomp_verify.py` (plain, `--units`, `--no-cpu`) proves the C bodies match the
   emulated ROM in lockstep.

4. The gallery and the UI never touch emulation state, and `dream --frames` is byte-identical

them, a defect on a path the gates do not cover, or a documentation claim that is wrong.

## High

### H1. A push that creates a branch runs no gate at all
`tools/hooks/pre-push:10-13`

For a new ref `remote_sha` is all zeros, so the hook sets `range="$local_sha"` and runs
`git diff --name-only "$local_sha"`, which diffs that commit against the working tree rather
than against its parent. On a clean tree the list is empty, `BUILD_SENSITIVE` is empty, and
`continue` skips `tools/check_no_rom.sh`, `make check` and `progress.py --check` for that ref.

Failure scenario: `git commit --no-verify` on a new branch, then `git push -u origin feature`.
Neither the IP scan nor the byte-identical gate runs. That is exactly the case the hook's own
header says it backstops.

Reproduced: in a scratch repo, `git diff --name-only $(git rev-parse HEAD)` printed nothing
while `git log --format= --name-only` printed `src/a.asm`.

The same silent skip happens when `remote_sha` names an object the local clone does not have:
`git diff` fails, `2>/dev/null` hides it, and `|| true` turns the failure into "nothing
build-sensitive".

Fix: derive the list from the commits (`git log --format= --name-only "$range"`), diff a new
ref against the empty tree (`git hash-object -t tree /dev/null`), drop `2>/dev/null || true`
so a git failure fails the push, and run `tools/check_no_rom.sh` unconditionally instead of
inside the build-sensitive branch.

### H2. `check_no_rom.sh` misses any path git has to quote
`tools/check_no_rom.sh:7-12` and `:19-21`

`git ls-files` C-quotes a path containing a non-ASCII or special byte, wrapping it in literal
double quotes. The `case` patterns then cannot match: `"data/\303\251.bin"` matches neither
`data/*` (leading quote) nor `*.bin` (trailing quote).

Failure scenario: a tracked `data/é.bin` or `baserom/ROM é.sfc` is committed and the scan
reports success. `.gitignore` is the first line of defence and still blocks the extensions,
so this needs `git add -f`, which is the case the scan exists to catch.

Reproduced: a scratch repo with `data/é.bin` added; `git ls-files` printed
`"data/\303\251.bin"` and the exact `case` block from the script printed MISSED.

Fix: `git ls-files -z | while IFS= read -r -d '' f`. Verified that form prints the unquoted
path and matches. Apply the same to the untracked loop.

### H3. Switching gallery pages mid-boot dereferences a freed machine
`recomp/app/scene.c:415` (`machine_free`), `recomp/app/scene.c:883-905` (`step_sprite`)

`machine_free` clears `sc->snes`, `sc->spMode` and `sc->spForcing`. It leaves `sc->spBooting`
true and leaves `sc->frame` where the other job left it. `step_sprite` then sees
`spMode != spWantMode` with `spBooting` already true, skips `machine_boot`, and calls
`machine_frame` (`snes_runFrame(sc->snes)`) or `sprite_draw` on a NULL machine.

Failure scenario: open Gallery > Sprite frames (live). `draw_sprites` issues
`scenes_sprite_request` and `step_sprite` starts a boot. Before it reaches `spBootTarget`,
pick Gallery > Scenes from the menu bar. `scenes_request` calls `machine_boot`, `phase`
becomes `JOB_BOOT`, and compose has priority in `scenes_step` (`scene.c:1405-1418`). The sweep
ends with `machine_free`. `spWanted` and `spBooting` are still set, and `main.c:1589` calls
`scenes_step` on every paused iteration whatever page is open, so the next iteration enters
`step_sprite` with `sc->snes == NULL`.

Verified by reading the whole chain. Not reproduced at runtime: no command-line flag
interleaves a `scenes_request` into a live sprite boot, and a 177-second
`--gallery-toggle 100,6000` run did not line the two jobs up. Treat it as a code-path finding.

Fix: clear `sc->spBooting` and `sc->frame` in `machine_free`, or guard `step_sprite` with
`if(sc->snes == NULL) sc->spBooting = false;` before the `!spBooting` test.

### H4. Both commit gates build the working tree, not the content being committed
`tools/hooks/pre-commit:33-39`, `tools/hooks/pre-push:18-27`

`pre-commit` runs `make -s check` against the working tree rather than the index. `pre-push`
checks that `HEAD` equals the pushed tip but never checks that the tree is clean, then runs
`make -s check` against that same possibly dirty tree.

Failure scenario: `git add -p` stages half an edit to `tools/names.txt`; the working tree,
carrying the whole edit, rebuilds byte-identically; the commit is created and pushed; the
committed tree does not rebuild. Guarantee 1 is false for the commit that lands on `main`,
and CI cannot catch it because CI has no ROM (`ci.yml:3-8`).

Fix: build the content being committed. `git stash push --keep-index` around the build in
`pre-commit` (restoring on exit), or assemble from `git archive` of the index and of
`$local_sha` in a temporary worktree. In `pre-push` also refuse a dirty tree.

## Medium

### M1. `--lockstep` prints a cycle divergence and passes anyway
`recomp/harness/main.c:2441-2453` (compare loop), `:2506-2513` (report)

`status` is set only by the seven `memcmp`s. The candidate's master-cycle and APU-cycle deltas
are computed as printf arguments only, in both the MISMATCH line and the final line.

Failure scenario: a wrong cycle charge drifts the candidate's clock without yet moving a
compared byte. The run prints `lockstep: N frames, no mismatches (candidate ended +312 master
cycles and +7 APU cycles from the reference)` and exits 0. `tools/recomp_verify.py:88-110`
keys success off the return code alone and never parses that number. So `docs/RECOMP.md:166-168`
and `recomp/README.md:596-597` describe an invariant nothing enforces. The `--unit` path does it
correctly at `main.c:2080-2085`.

Fix: compare `cand.snes->cycles` against `ref.snes->cycles` and the two `apu->cycles` after
the region loop, and set `status = 1` on a difference.

### M2. `--no-cpu` is the only mode the shipped game runs in, and no gate runs it
`recomp/app/main.c:1435-1436`, `Makefile:151-152`, `tools/hooks/pre-commit:44-58`

`recomp/app/main.c:1435-1436` calls `ss_nocpu_enable(&m.ss, true)` and `sps_nocpu_enable(&m.sps, true)`
unconditionally. `make recomp-check-nocpu` exists and is referenced by nothing:
`grep -rn 'recomp-check-nocpu' tools/hooks .github/workflows` returns nothing. The pre-commit
hook runs `make recomp-check` and `make recomp-check-units` only.

Failure scenario: a routine is added whose tail `jmp` lands on an address with no registry
row. Under `--hooks on` the emulated CPU executes it and lockstep passes, so pre-commit,
pre-push and CI all pass. Under `--no-cpu` the scheduler hits `ss_nocpu_no_body`
(`recomp/harness/snes_state.c:595-611`), prints a message prefixed `dream_harness:` and calls
`exit(3)`. The player's game vanishes.

Verified today: `--no-cpu --lockstep` passes on `title_start_right` (300 frames),
`level_walk_jump` (3700) and `mode_cycle` (900), each at +0 master and +0 APU cycles.

Fix: add `make recomp-check-nocpu` to the pre-commit hook's `recomp/` branch.

### M3. The routine-level gate passes having run nothing
`tools/recomp_verify.py:119-121`, `recomp/harness/main.c:2143-2178`

`run_units()` returns `ok=True` when `config/recomp_units.txt` is absent. When the file is
present but holds only comments, the harness prints `unit: 0 seeds over 0 routines, 0 failed`
and exits 0, so the wrapper reports a pass with an empty credit set.

Reproduced: pointing `UNITS_TXT` at a missing path returned
`(True, {}, [], 'units.txt not present: no routine-level gate')` without launching the
harness. A comment-only spec file gave `unit: 0 seeds over 0 routines, 0 failed`, rc 0.

`make recomp-check-units` and the pre-commit hook both report success in that state, while
the 42 routines marked `; unit` in `config/recomp.txt` keep their dashboard credit.

Related: `recomp/README.md:566` and `docs/RECOMP.md:20-21` promise "at least four seeds each".
Nothing enforces it. `recomp_verify.py` parses the seed count and never compares it to 4. The
data complies today (42 routines, none under 4).

Fix: exit 2 when the spec is missing or yields zero seeds, and require four seeds before a
routine is credited `; unit`.

### M4. `config/recomp.txt` is never checked against a gate run
`tools/recomp_verify.py:239-266`, `tools/progress.py:190-197`

The file is written only under `--update`. In gate mode `recomp_verify.py` prints `*` beside
routines no script entered and still returns 0, and `progress.py` credits the traced size of
any name in the file without checking that the name is still registered, still entered, or
still passing.

Failure scenario: a routine is deleted from `recomp/src/`, renamed, or becomes unreachable by
every script. `make recomp-check` passes, the hook passes, and the `recomp` badge keeps
counting its bytes. `docs/RECOMP.md:13-14` says a routine is recomped "only when its C body
passes that check across the test scripts".

No drift today: the run I made credits 126 + 66 by script plus 42 by unit = 234, and
`config/recomp.txt` holds exactly 234 entries.

Fix: add a `--check` mode that recomputes `called | unit_only` and exits non-zero when it
differs from the committed file, and call it from `make recomp-check`.

### M5. `roundtrip_check.py` reports 100% for a kind whose files are missing
`tools/roundtrip_check.py:78-80`, `:131-132`, `:164`

A missing asset file increments `missing` and `continue`s before `st['total'] += 1`, so it is
invisible to the per-kind ratio. `missing` affects neither `pass == total` nor the exit code.

Failure scenario: `config/assets.txt` gains asset paths and `make extract` has not re-run (the
`$(HALVES)` rule does not depend on `config/assets.txt`). `make roundtrip` reports the kind at
100%, `--update` promotes it into `config/roundtrip.txt`, and `tools/progress.py:232` credits
every byte of that kind as matched.

Reproduced: a two-row manifest with one real `brr` asset and one non-existent path printed
`brr 1 1 100.0%`, noted one missing file, wrote `brr` into the generated file, and exited 0.

Fix: count a missing asset as a failure, or at least increment `total` without `pass`, and
return non-zero when `missing` is non-zero or no asset was checked.

### M6. The palette observation pass resumes on the machine a sprite job left behind
`recomp/app/scene.c:1379` (`step_observe`)

`step_observe` boots a fresh machine only when `sc->snes == NULL || sc->obsFrame == 0`.
`step_sprite`'s `machine_boot` replaces `sc->snes` without resetting `obsFrame` or
`obsScript`, so an interrupted observation pass carries on counting script frames on the
sprite machine.

Failure scenario: the Sprites page requests both. `main.c:1587-1589` runs `scenes_step` before
`gallery_render` issues the sprite request, so iteration 1 boots the observation machine and
`obsFrame` goes non-zero; iteration 2 lets `spWanted` preempt it; `machine_boot` throws the
observation machine away; once `sprite_draw` returns, `observe_frame()` resumes on a machine
in a different scene with `entity_count` forced to 2 and slots 1-15 set to `ENTITY_TYPE_NONE`
by `sprite_force_entities`. The page then labels contaminated data "OBSERVED ... seen in OAM",
which `recomp/app/README.md:330` calls "a measurement, not a second derivation".

The headless reports are unaffected: `--frames 1 --sprite-pal-report` and
`--frames 1 --gallery sprites --sprite-pal-report` both print
`194 observed, 869 derived only, 492 unknown`, matching the README.

Fix: reset `obsFrame` and restart the script whenever `machine_boot` runs for a different job,
or give the observation pass its own `Snes*`.

### M7. The 8bpp tileset page draws uninitialised stack as colour
`recomp/app/gallery.c:1839` (`uint32_t rgb[256]`), written at `:1872`, read at `:1883`, `:1885`

In `draw_bg_raw`'s override branch, `pal_override()` fills `rgb[0..15]` only.
`draw_tile_grid(..., bpp, ...)` with `bpp == 8` indexes `rgb[v]` for `v` up to 255, and

Reproduced: `--frames 1 --gallery "backgrounds:brrrrrd" --screenshot ...` (the one

checker colours allow at most 18. The extra colours are whatever the previous `draw_bg_raw`

### M8. The CI and release DLL check is far weaker than the Makefile's
`.github/workflows/ci.yml:114`, `.github/workflows/release.yml:115`

Both jobs test `objdump -p "$exe" | grep -Eiq 'DLL Name: *(lib|SDL3\.dll)'`. That flags only a
DLL whose name starts with `lib` and `SDL3.dll` itself. `Makefile:108-131` uses an explicit
allowlist of Windows system DLLs and fails on anything else.

Failure scenario: the build starts importing `zlib1.dll`, `libwinpthread` under a different
name, or an MSYS2 runtime DLL that does not begin with `lib`. CI passes, the release job
passes, and the zip ships an executable that cannot start on a clean Windows machine. The
release workflow's own header calls the three-file count a gate rather than a promise; the
DLL half of that promise is not gated to the same standard.

Fix: move the Makefile's allowlist into a script and call it from all three places.

### M9. `make -j` runs `tools/extract.py` concurrently on the same output files
`Makefile:17-18`

`$(HALVES): $(ROM) tools/extract.py` is a plain multi-target rule, so GNU make treats the
recipe as building one target per invocation. Under `-j` it starts one process per job slot.

Reproduced with the same rule shape in a scratch Makefile: serial `make` ran the recipe once,
`make -j8` ran it nine times concurrently.

`tools/extract.py:45-46` opens each file with `'wb'`, which truncates. Two processes
interleaving a truncate and a write on the same file leave a short or hole-punched
`data/NN.bin`. asar then reads it and `make -j check` fails for a reason that has nothing to
do with the sources. The failure is loud, so guarantee 1 is not silently broken, but the
build is not safe to parallelise.

Fix: use a stamp target (`data/.extracted: $(ROM) tools/extract.py` with
`$(HALVES): data/.extracted ;`), or GNU make 4.3's grouped-target `&:`.

### M14. The `jsl` into `anim_update` pushes its return address without the interrupt latch
`recomp/src/anim.c:59`

The body pushes the return address with `ss_push16()`, which writes high then low with nothing
in between. `recomp/harness/snes_state.c:286-289` confirms that. LakeSnes' `case 0x22` pushes
it with `cpu_pushWord(cpu, cpu->pc - 1, true)`, and `cpu_pushWord`'s `intCheck` puts a
`cpu_checkInt()` between the two bytes.

```
  C099D8  22 C8 AE 80  jsl anim_update              ; m0x0
  C099DC  60           rts                          ; m0x0
```

Every other `jsl` and `jsr` in the port models the latch: `entities_ai.c:99-103`,
`anim_scripts.c:71-73`, `top_level.c:279-281`, `oam_emit.c:282-284`, `vram_stream.c:93-95`,
`scroll.c:89-91`, `mode_init.c:119-121`. This site is the outlier.

Failure scenario: the NMI line rises during the two cycles the return address is pushed. The
ROM latches it and services the NMI before `anim_update`'s first instruction. The hook does
not, so `ss_run_callee`'s `ss_yield_wanted` (`snes_state.c:389`, which reads `cpu->intWanted`)
answers false and `anim_update` runs an instruction or two before the NMI is taken. The pushed
pc and the stack bytes below `$01FF` then differ, which is what the WRAM compare looks at.

The unit gate cannot see it either: `ss_unit_hold` makes `ss_yield_wanted` return false
(`snes_state.c:385`) and no interrupt is enabled during a unit run. `anim_rate_store` is the
shared tail of all seven rate handlers, three of which are credited by the unit gate alone.

Fix:
```c
{ const uint16_t ret = (uint16_t)(ss_pc(ss) - 1);
  ss_push8(ss, (uint8_t)(ret >> 8)); ss_check_int(ss); ss_push8(ss, (uint8_t) ret); }
```

## Low

### L1. `--only` with a name that matches nothing reports a clean lockstep pass
`recomp/harness/main.c:2349-2361`

The filter compacts both tables without checking that anything survived. Reproduced:
`--lockstep --hooks on --only no_such_routine --frames 5` printed
`table all (0 entries, 0 cycle-costed, 0 spc)` and `lockstep: 5 frames, no mismatches`, rc 0.
A typo in a bisection proves nothing while looking green.

Fix: exit 2 when a `--only` name matches neither registry.

### L2. A repeated `stack=` key writes past `sd->stack[]`
`recomp/harness/main.c:1606-1613`

The guard checks this token's length against `UNIT_MAX_STACK` (8) and never checks the
accumulated `sd->stackCount`. Reproduced under `-fsanitize=undefined` with a seed line
carrying two `stack=` keys:
`main.c:1610:16: runtime error: index 8 out of bounds for type 'uint8_t [8]'`, and the seed
still reported `unit pass`. The first overflowing byte lands on `sd->stackCount` itself
(`main.c:1501-1502`), so the loop bound becomes data-controlled.

`config/recomp_units.txt` is a trusted committed file, so this is robustness.

Fix: `if(n == 0 || (n & 1) != 0 || sd->stackCount + (int)(n / 2) > UNIT_MAX_STACK) return false;`

### L3. `ss_consume_cycles` drops one cycle from an odd charge, every call
`recomp/harness/snes_state.c:448-455`

`step &= ~1;` then `if(step == 0) break;` means a remaining budget of 1 is discarded, so a
hook with an odd `cycleCost` is charged `cycleCost - 1`. Rounding is necessary because
`snes_runCycles` advances two at a time, but it rounds down silently and forever. With M1 the
drift would accumulate without failing the gate.

Latent today: all 28 entries in `config/recomp_cycles.txt` are 0 (verified).

Fix: carry the dropped cycle into the next call, or reject an odd charge at load time.

### L4. Direct-page address arithmetic is masked in some bodies and not others
`recomp/src/random.c:69` and 163 similar sites across 11 files in `recomp/src/`

`t_rol8_dp` (`random.c:41-43`) masks the effective address to 16 bits, which is what the 65816
does for direct-page addressing in native mode. The direct `t_read8(ss, dp + 0x9D)` /
`t_write8(ss, dp + init_magic_AA55)` calls do not. Counted: 164 unmasked `dp + X` forms
against 388 masked `(uint16_t)(dp + ...)` forms. `t_read16` additionally carries into the bank
byte (`(adr + 1) & 0xffffff`), where a direct-page 16-bit read wraps inside bank 0.

Unreachable today: this ROM keeps D at `$0000` and `dream_alu.h:6` records that. It is a
latent transcription hazard if a routine is ever converted that runs with D set.

Fix: route every direct-page access through one helper that masks.

### L5. The two coroutine backends refuse different misuses
`recomp/harness/coro_ucontext.c:101-105`, `:120-122`; `recomp/harness/coro_fibers.c:117-126`, `:161-171`

`coro.h:17` says the contract is identical on both. `coro_resume` on a never-started coro:
fibers prints an error and exits 2, ucontext swaps into the all-zero `ucontext_t` left by
`calloc`. `coro_free` on the running coro: fibers refuses, ucontext frees the stack it is
executing on and keeps running. Neither is reachable from the current scheduler.

Fix: mirror the two guards in the ucontext backend.

### L6. The coroutine stacks are `malloc`ed with no guard page
`recomp/harness/coro_ucontext.c:94`, `recomp/harness/snes_state.c:542`

`SS_NOCPU_STACK` is 512 KiB per context, up to 8 contexts. `CreateFiberEx` gives the Windows
fibers a guard page; `malloc` does not. A body-chain stack overflow is a trapping fault on
Windows and a silent heap write on POSIX. Observed depth in the runs I made is 1 stack and 6
nested hooks, so there is ample headroom.

Compounding: `recomp/app/dlog.c:371-400` installs the signal handlers with plain `signal()`
and no `sigaltstack`, so a stack overflow that does fault produces no log.

Fix: `mmap` the stacks with a `PROT_NONE` guard page, and install `SIGSEGV` on an alternate
stack.

### L7. `dream.log` is truncated by the next run, including after a crash
`recomp/app/dlog.c:174-176`

`dlog_open` does `fopen(path, "w")` at a fixed path with no locking. The next launch from the
same directory truncates it.

Failure scenario: the game crashes, the player relaunches to see whether it happens again, and

### L20. `jmp abs` is modelled without its interrupt latch at 33 sites
`recomp/src/particles.c:27`, `oam_emit.c:1135`, `vram_stream.c:714`, `anim_scripts.c:332`,
`entities.c:218`, `entities_ai.c:206`, `particles_fx.c:134` and 26 more

LakeSnes' `case 0x4c` is `cpu->pc = cpu_readOpcodeWord(cpu, true);` (`cpu.c:1330-1332`), so a
`cpu_checkInt()` sits between the low and high operand bytes. `S(addr, 3)` issues three
consecutive fetches with no latch.

The port already knows this. `top_level.c:192-195` defines `SJMP` as `t_step(...,2)` plus
`ss_check_int` plus `ss_fetch(1)`, with the comment "jmp abs: opcode, low byte, latch, high
byte (LakeSnes case 0x4c)", and `mode_init.c:144-151` defines `t_jmp_abs` the same way. 37
sites use the latched form, all in those two files. 33 do not: `particles_fx.c` 13,
`anim_scripts.c` 6, `oam_emit.c` 6, `vram_stream.c` 4, `entities_ai.c` 2, `entities.c` 1,
`particles.c` 1.

`mode0_particle_draw_dispatch` (`particles.c:24-29`) is the sharpest case. It is a bare tail
jump: the body sets the pc and returns, so nothing later in the body re-latches, and the
emulator's next `cpu_runOpcode` reads a stale `intWanted`.

Fix: move `SJMP` into `dream_time.h` and use it at those 33 sites.

### L21. The latch inside a 16-bit immediate operand is modelled in 2 of 14 files
`recomp/src/top_level.c:185-189`, `recomp/src/sound_iface.c:77-81` (modelled);
860 sites in 12 other files (not modelled)

`cpu_adrImm` only advances the pc (`cpu.c:311-319`); the opcode body then reads the operand
with `cpu_readWord(low, high, true)`, so the latch sits between the two operand bytes.
`SIMM16`/`SIMM8` exist for exactly this and carry a comment saying so. Per-file counts of
latched against plain: `top_level.c` 250/0, `sound_iface.c` 36/0, and 0/N everywhere else
(`mode_init.c` 393, `particles_fx.c` 127, `vram_stream.c` 98, `anim_scripts.c` 55,
`entities_ai.c` 53, `scroll.c` 43, `oam_emit.c` 33, `entities.c` 20, `oam.c` 19,
`ppu_dma.c` 13, `camera.c` 5, `input.c` 1).

No case where this is observed in the current scripts was found. In normal operation the NMI
is taken while the CPU is parked on `wai` at `$C0:A4FD`, and `cpu_runNonInstruction`'s
`waiting` branch tests `nmiWanted` directly rather than `intWanted` (`cpu.c:114-122`), so the
park path is immune. It matters only when a frame's work overruns into vblank. The two files
that do model it are the two whose timing was already found to matter, so the omission
elsewhere may be deliberate.

Fix: apply it uniformly, or record the reasoning in `dream_time.h` beside `SIMM16`.

### L22. Absolute-indexed effective addresses are truncated to 16 bits before the bank is added
`recomp/src/entities_ai.c:533`, `:536`, `:553`, `:556`, and the same shape throughout `recomp/src`

```c
S(0x998E, 3); t_index(ss);            /* C0998E lda entity_state_anim_table,Y */
a = t_read16(ss, ss_abs(ss, (uint16_t) (entity_state_anim_table + y)));
```

`ss_abs` (`dream_alu.h:15-18`) takes a `uint32_t` and would carry into the bank correctly. The
`(uint16_t)` cast at the call site wraps `base + index` inside the bank first.
`cpu_adrAby` does the add in 24 bits: `*low = ((cpu->db << 16) + adr + cpu->y) & 0xffffff`
(`cpu.c:419-425`), so the real instruction crosses into `DB+1`.

Failure scenario: `Y` at `$998E` is not a bounded slot index. It is
`entity_state + $0BAC + entity_state_anim_table[type]`, built by two `adc`s at `$9987` and
`$998A` and moved to Y by the `tay` at `$998D`. With `entity_state_anim_table = $B7AE`, any
`Y >= $4852` makes the ROM read `$81:xxxx` while the C reads `$80:xxxx`. That is a wrong data
word, not a timing skew. The same shape is at `$99A2` and `$99A6` for `anim_rate_fn_table`.
Today the table values keep Y small, so it never fires; it is reachable only through a
corrupted `entity_state` or `$0BAC`.

Fix: drop the `(uint16_t)` cast at `ss_abs` call sites that add an index, letting the 24-bit
add in `ss_abs` do the carry. This applies only to `ss_abs`. The direct-page-indexed forms do
wrap at 16 bits and must keep their cast (see L4).
